ONPAR 학습지

이벤트 소싱, 결과 말고 과정을 저장하기

지금의 결과 대신, 거기까지 온 과정을 전부 저장하는 방식

입문본학습 25분연습 12분선택 과제 35분

이 학습지는 이걸 안다고 봐요데이터베이스에 표와 행이 있다는 걸 안다함수를 하나쯤 써본 적이 있다이벤트 소싱은 처음이어도 된다

01

무엇을 배우는가

가계부를 떠올려 보세요. 남은 돈만 적나요, 쓴 내역을 하나씩 적나요? 대부분 내역을 적을 거예요. 그래야 나중에 "이 돈 어디 갔지?"에 답할 수 있으니까요. 이벤트 소싱은 컴퓨터에 그 방식을 쓰는 거예요.

보통 프로그램은 지금 상태를 저장해요. 잔액 12,000원, 주소 서울 어딘가. 이벤트 소싱은 그 대신 일어난 일들을 순서대로 저장해요. 지금 상태가 궁금하면 그 목록을 처음부터 더해서 계산합니다.

이 학습지를 마치면

  • 상태를 저장하는 것과 변화를 저장하는 것의 차이를 예로 들어 설명하기
  • 이벤트를 왜 고치면 안 되는지 이유 말하기
  • 이벤트 소싱을 쓰지 말아야 할 상황 하나 이상 대기

먼저 풀고 갈 말들

이벤트(Event)
이미 일어난 일 하나를 가리켜요. '5만원 출금됨' 같은 거예요. 앞으로 하겠다는 게 아니라 이미 벌어진 일이라는 게 중요해요.
이벤트 스토어(Event Store)
이벤트를 순서대로 쌓아두는 곳이에요. 이름은 거창하지만 하는 일은 장부와 같아요. 새로 적기만 하고 지우지 않아요.
append-only(어펜드 온리)
'덧붙이기만' 이라는 뜻이에요. 새로 쓰는 건 되고 이미 쓴 걸 고치거나 지우는 건 안 돼요.
리플레이(Replay)
쌓인 이벤트를 처음부터 다시 훑어서 지금 상태를 계산하는 걸 말해요. 가계부를 위에서부터 더해 잔액을 내는 것과 같아요.
상태(State)
지금 이 순간의 값이에요. 잔액 30만원처럼요. 이벤트 소싱에서는 이걸 저장하지 않고 그때그때 계산해요.
파르

이걸 처음 보면 '그래서 잔액은 어디에 저장하는데?' 부터 막혀요. 답은 '저장 안 해요' 예요. 매번 계산하거든요. 이 한 줄만 넘기면 나머지는 술술 풀려요.

02

이것이 생기기 전에는

예전 시스템은 잔액 칸 하나를 계속 덮어썼어요. 12,000원이 3,000원이 되면 12,000은 그냥 사라졌습니다. 나중에 "왜 3,000원이죠?" 라고 물어도 답할 방법이 없었어요.

그때의 불편

  • 왜 이 값이 되었는지 알 수 없어요. 덮어쓴 순간 이유가 함께 사라지니까요
  • 잘못 고친 걸 되돌리려면 백업 전체를 되살리는 수밖에 없어요
  • 은행이나 병원처럼 기록을 남겨야 하는 곳에서는 따로 기록용 표를 손으로 관리해야 했어요

그래서 무엇이 필요했나

그런데 이 문제는 이미 수백 년 전에 풀려 있었어요. 회계 장부예요. 장부는 틀렸다고 지우지 않아요. 반대 내용을 새로 적습니다. 이벤트 소싱은 그 방식을 프로그램으로 옮겨온 거예요.

03

먼저 보면 좋은 학습지

불변성(Immutability)

이벤트를 고치지 않는다는 게 이 방식의 전부예요. 이 개념이 없으면 6번 본론에서 "그냥 고치면 되잖아?" 에서 막히실 거예요.

한 번 만든 값은 바꾸지 않는다는 생각

도메인 이벤트

저장할 일들을 어떻게 이름 붙이고 나눌지가 실무에서는 제일 어려운 부분이에요. 미리 보시면 6번이 편해져요.

업무에서 의미 있는 사건을 과거형 이름으로 적은 것

멱등성(Idempotency)

이벤트를 몇 번 다시 훑어도 결과가 같아야 해요. 이 성질이 왜 필요한지 알면 리플레이가 훨씬 자연스럽게 읽혀요.

같은 일을 여러 번 해도 결과가 같은 성질

04

탄생 배경

  • 아주 오래전

    복식부기라는 회계 방식이 자리를 잡았어요. 틀린 기록을 지우지 않고 반대 기록을 새로 적어서 바로잡는 방식이에요.

  • 2010년대

    Kafka 같은 기술이 널리 쓰이면서 '기록이 곧 진실' 이라는 생각이 자연스러워졌어요.

이벤트 소싱은 누가 딱 발명했다기보다 여러 갈래가 만난 자리에 가까워요. 회계 장부, 데이터베이스가 안에서 쓰는 기록, 개발자들이 쓰는 버전 관리. 전부 같은 생각이에요. 변화를 지우지 말고 쌓아두자는 것이죠.

05

상황극 & 예시

은행 고객센터예요. 손님이 잔액이 이상하다며 찾아왔고, 개발자 민아 씨가 불려 나왔어요.

손님

분명히 50만원 있었는데 지금 30만원이에요. 왜 이렇게 됐죠?

민아

잠시만요... 화면에 잔액 300,000 이라고만 적혀 있네요.

손님

그러니까 왜 그렇게 됐냐고요.

민아

저희 시스템이 지금 얼마인지만 저장하고 있어서요. 어떻게 그렇게 됐는지는 남아 있지 않아요.

손님

은행이 그래도 되나요?

그래서 무슨 뜻이냐면

이벤트 소싱이었다면 민아 씨 화면에 이렇게 떴을 거예요. 입금 500,000 / 출금 150,000 / 출금 50,000. 잔액은 이 목록을 더한 결과일 뿐이고, 진짜는 목록 쪽이에요. 답할 수 있는 시스템과 그러지 못하는 시스템의 차이가 여기서 갈려요.

실제로 있었던 일은 아니고, 이해를 돕기 위해 만들어 본 상황이에요. 다만 지금 상태만 저장하는 시스템이 이런 질문에 답하지 못하는 문제 자체는 실제로 자주 생겨요.

06

본론

이벤트 이름은 과거형으로 지어요

약속을 잡는 것과 만난 것은 다르죠. 약속은 취소될 수 있지만 이미 만난 건 되돌릴 수 없어요. 이벤트도 그래요. 이미 일어난 일이라서 이름이 과거형이에요. WithdrawMoney 는 '출금해 줘' 라는 부탁이고, MoneyWithdrawn 이 '출금됐다' 는 이벤트예요. 부탁은 거절할 수 있지만 일어난 일은 거절할 수 없어요.

같은 상황을 부탁과 사실로 나눠 적어 보면

// 부탁 — 거절될 수 있어요
{ type: 'WithdrawMoney', accountId: 'A1', amount: 50000 } // 이벤트 — 이미 일어난 일이라 되돌릴 수 없어요
{ type: 'MoneyWithdrawn', accountId: 'A1', amount: 50000, at: '2026-09-06T10:00:00Z' }

골라 보세요

'OrderCancel', 'OrderCancelled', 'CancelOrder' 중 이벤트 이름으로 알맞은 것은?

  1. ①OrderCancel
  2. ②OrderCancelled
  3. ③CancelOrder
답하고 나서 열기
OrderCancelled 예요. 이미 일어난 일이라 과거형이에요. CancelOrder 는 '취소해 줘' 라는 부탁이고, OrderCancel 은 어느 쪽인지 애매해서 팀이 섞어 쓰게 돼요.

흔한 실수

이름을 현재형으로 짓는 거예요. 그러면 팀이 부탁과 사실을 섞어 쓰게 되고, 이벤트 스토어에 '하려다 실패한 일' 까지 들어가 버려요.

상태는 저장하지 않고 그때그때 계산해요

잔액이 필요하면 그 계좌의 이벤트를 위에서부터 하나씩 더해요. 가계부 잔액을 손으로 더하는 것과 똑같아요. 이걸 리플레이 라고 불러요. 어려운 말 같지만 하는 일은 그냥 더하기예요.

이벤트 목록을 더해서 잔액을 만들어요

const balance = events.reduce((sum, e) => e.type === 'MoneyDeposited' ? sum + e.amount : e.type === 'MoneyWithdrawn' ? sum - e.amount : sum
, 0)

직접 계산해 보세요

입금 30,000 / 출금 12,000 / 입금 5,000 / 출금 8,000 을 위에서부터 더해 잔액을 구해 보세요.

답하고 나서 열기
15,000 이에요. 30,000 − 12,000 + 5,000 − 8,000. 이게 리플레이예요. 잔액이라는 칸은 어디에도 없고, 필요할 때 이렇게 계산해요.

흔한 실수

이벤트가 수만 개 쌓인 뒤에도 매번 처음부터 더하는 거예요. 중간 결산을 하나 저장해 두고 그 뒤부터만 더하면 돼요.

한 번 적은 이벤트는 고치지 않아요

잘못 적었으면 어떻게 할까요. 지우는 게 아니라 바로잡는 이벤트를 새로 적어요. 장부에서 지우개를 쓰지 않는 것과 같아요. 이 규칙을 한 번이라도 어기면 '기록이 진실' 이라는 약속이 깨지고, 이 방식의 장점이 통째로 사라져요.

골라 보세요

출금 12,000 이 사실은 21,000 이었어요. 어떻게 바로잡을까요?

  1. ①12,000 을 21,000 으로 고친다
  2. ②'출금 정정 +9,000' 이벤트를 새로 덧붙인다
  3. ③12,000 을 지우고 21,000 을 새로 적는다
답하고 나서 열기
정정 이벤트를 덧붙여요. 고치거나 지우면 '기록이 진실' 이라는 약속이 깨지고, 예전에 계산했던 값들과 어긋나서 원인을 찾을 수 없게 돼요. 장부에 지우개를 안 쓰는 것과 같아요.

흔한 실수

"이번 한 번만 데이터베이스에서 직접 고치자" 는 유혹이에요. 그 순간부터 다시 계산한 값과 실제가 어긋나고, 원인을 찾는 데 며칠이 걸려요.

그래서 언제 쓰면 안 될까요

이 방식은 공짜가 아니에요. 조회가 번거로워지고, 팀 전체가 이 개념을 알아야 해요. 판단 기준은 하나예요. '어쩌다 이렇게 됐는지' 를 아무도 묻지 않는 곳이라면 쓰지 않는 게 좋아요. 사내 공지 게시판에 이걸 얹는 건 짐만 늘리는 일이에요.

흔한 실수

멋져 보인다는 이유로 시스템 전체에 적용하는 거예요. 보통은 계좌나 주문처럼 기록이 중요한 일부에만 써요.

07

꿀팁

이벤트 이름은 현업에서 쓰는 말 그대로

'주문완료됨' 을 개발자가 'OrderStatusUpdated' 로 바꾸는 순간 코드와 대화가 어긋나요. 기획자와 상담원이 알아듣는 이름이 좋은 이름이에요.

계산한 값은 이벤트에 넣지 않기

'출금 5만원' 만 적고 '남은 잔액 30만원' 은 적지 마세요. 나중에 계산 방식이 바뀌면 과거 기록이 전부 틀린 말이 되어 버려요.

중간 결산은 느려진 다음에

처음부터 넣으면 복잡해지기만 해요. 저는 이벤트 몇 백 개짜리에 중간 결산을 넣었다가 괜히 버그만 만들었어요. 수천 개까지는 그냥 더해도 빨라요.

이벤트에 버전 번호를 미리 넣어두기

저장하는 모양은 언젠가 바뀌어요. 버전이 없으면 예전 이벤트를 어떻게 읽어야 할지 알 방법이 없어요. 저는 이거 안 넣었다가 나중에 고생했어요.

08

질의 5개

  1. 이벤트 스토어에 저장하는 것은 '지금 상태' 인가요, '일어난 일' 인가요?

    정답 보기

    정답일어난 일(이벤트)이에요. 지금 상태는 그 일들을 처음부터 더해서 계산해요.

    이게 이벤트 소싱의 정의예요. 상태는 저장하는 대상이 아니라 계산한 결과예요.

    이렇게 답했다면

    • 지금 상태를 저장하고 이벤트는 로그로만 — 그러면 상태가 진실이고 이벤트는 참고가 돼요. 이벤트 소싱은 반대로 이벤트가 진실이에요.

  2. 다음 중 이벤트 이름으로 알맞은 것은 무엇일까요?

    • WithdrawMoney
    • MoneyWithdrawn
    • WithdrawingMoney
    • MoneyWithdrawRequest
    정답 보기

    정답MoneyWithdrawn

    이벤트는 이미 일어난 일이라 과거형이에요. WithdrawMoney 는 거절될 수 있는 부탁이고, Request 는 아직 일어나지 않은 요청이에요.

    이렇게 답했다면

    • WithdrawMoney — 부탁은 거절될 수 있어요. 거절될 수 있는 것은 '일어난 일' 이 아니에요.

  3. 온라인 쇼핑몰에서 고객이 "왜 내 포인트가 3,000 이죠?" 라고 물었어요. 지금 상태만 저장하는 시스템과 이벤트 소싱 시스템은 각각 무엇이라고 답할 수 있을까요?

    정답 보기

    정답상태만 저장하면 "3,000 입니다" 밖에 못 해요. 이벤트 소싱이면 적립·사용·소멸 내역을 순서대로 보여주며 어떻게 3,000 이 됐는지 설명할 수 있어요.

    기록이 있느냐 없느냐가 답할 수 있느냐를 정해요. 상황극의 은행 장면과 같은 구조인데 도메인만 바뀐 거예요.

    이렇게 답했다면

    • 상태 시스템도 로그를 뒤지면 된다 — 별도 로그가 있다면 그게 이미 이벤트를 따로 쌓는 셈이에요. 상태 칸 하나만 있으면 이유는 사라져요.

  4. 동료가 이벤트에 '이번 거래 후 잔액' 을 함께 넣자고 해요. 6개월 뒤 수수료 계산 규칙이 바뀌면 무슨 일이 생길까요?

    정답 보기

    정답과거 이벤트에 박힌 잔액이 전부 새 규칙과 어긋나는 거짓 기록이 돼요. 잔액을 안 넣었다면 새 규칙으로 처음부터 다시 계산하면 그만이에요.

    이벤트는 일어난 사실만 담아요. 계산된 값은 규칙이 바뀌면 과거까지 틀리게 만들어요. 필요할 때 계산하면 규칙 변경에도 안전해요.

    이렇게 답했다면

    • 조회가 빨라지니 넣는 게 낫다 — 빠른 조회는 중간 결산이나 읽기용 표로 따로 해결해요. 이벤트 자체에 계산값을 넣으면 안 돼요.

  5. 두 시스템이 있어요. ① 병원의 처방 기록 ② 회사 인트라넷의 점심 메뉴 투표. 각각 이벤트 소싱을 쓸지 말지 정하고, 한 줄씩 이유를 써 보세요.

    정답 보기

    정답① 씁니다 — 누가 언제 무엇을 처방했고 왜 바뀌었는지가 법적으로도 중요해요. ② 안 씁니다 — 오늘 결과만 있으면 되고 과거 투표 경위를 아무도 안 물어요.

    기준은 '어쩌다 이 값이 됐는지를 누군가 묻는가' 예요. 처방 기록은 묻고, 점심 투표는 안 물어요. 기술이 멋져서가 아니라 질문이 있느냐로 정해요.

    이렇게 답했다면

    • 둘 다 쓴다 — 기록은 많을수록 좋으니까 — 점심 투표에 이벤트 소싱을 얹으면 조회만 번거로워지고 배울 것만 늘어요. 이력을 묻지 않는 곳에서는 비용만 남아요.
파르

막히면 본론으로 돌아가서 다시 읽어도 괜찮아요. 외워서 맞히는 것보다 왜 그런지 떠올려 보는 게 훨씬 오래 남아요.

  • 같이 쓰는 문서에서 되돌리기와 편집 기록을 만들 때

일상에 붙이기

코드 밖에서도 써먹을 수 있어요. 가계부를 '남은 돈' 이 아니라 '쓴 내역' 으로 적는 것, 일기를 '요즘 힘들다' 가 아니라 '오늘 무슨 일이 있었다' 로 적는 것이요. 결론 말고 사건을 남겨두면 나중에 다른 결론도 꺼낼 수 있어요. 오늘 일기부터 한번 그렇게 써보셔도 좋겠어요.
