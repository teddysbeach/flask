ONPAR 학습지

이벤트 소싱, 상태 대신 변화를 저장하기

지금의 상태 대신, 거기까지 온 모든 변화를 저장하는 방식

입문약 28분문제 5개

01무엇을 배우는가

우리는 보통 데이터베이스에 지금의 상태를 저장합니다. 잔액 12,000원, 주소 서울시 어딘가. 이벤트 소싱은 그 대신 일어난 일의 목록을 저장하고, 상태는 그 목록을 처음부터 훑어 계산해냅니다.

이 학습지를 마치면

  • 상태 저장과 이벤트 저장의 차이를 예를 들어 설명할 수 있다
  • 이벤트 스토어가 append-only 여야 하는 이유를 말할 수 있다
  • 이벤트 소싱을 쓰면 안 되는 상황을 세 가지 댈 수 있다

02이것이 생기기 전에는

예전 계좌 시스템은 잔액 칸 하나를 계속 덮어썼습니다. 12,000원이 3,000원이 되면 12,000은 그냥 사라집니다. 문제가 생겨 "왜 3,000원이죠?"라고 물으면 답할 방법이 없었습니다.

그때의 불편

  • 왜 이 값이 되었는지 추적할 수 없다 — 덮어쓴 순간 이유가 사라진다
  • 잘못된 수정을 되돌리려면 백업 전체를 복원하는 수밖에 없다
  • 감사(audit)가 필요한 금융·의료 도메인에서 별도 로그 테이블을 손으로 관리해야 한다

그래서 무엇이 필요했나

그런데 회계는 수백 년 전부터 이 문제를 풀어놨습니다. 장부는 잔액을 고쳐 쓰지 않습니다. 틀리면 반대 분개를 새로 적습니다. 이벤트 소싱은 그 방식을 소프트웨어로 옮긴 것입니다.

03먼저 보면 좋은 학습지

불변성(Immutability)

이벤트가 절대 수정되지 않는다는 전제가 이벤트 소싱의 모든 장점을 만듭니다. 이걸 모르면 "왜 그냥 고치면 안 되지?"에서 막힙니다.

한 번 만들어진 값은 바꾸지 않는다는 설계 원칙

도메인 이벤트

저장할 이벤트를 어떻게 이름 짓고 나눌지가 이벤트 소싱의 8할입니다.

업무상 의미 있는 사건을 과거형으로 표현한 것

멱등성(Idempotency)

이벤트를 다시 읽어 상태를 재구성하는 과정이 몇 번을 해도 같아야 합니다.

같은 연산을 여러 번 해도 결과가 같은 성질

04탄생 배경

  • 회계의 역사

    복식부기는 기록을 지우지 않고 반대 분개를 추가하는 방식으로 정확성을 지켜왔습니다.

  • 2005년경

    Greg Young 과 Udi Dahan 을 중심으로 DDD 커뮤니티에서 이벤트 소싱과 CQRS 가 함께 논의되기 시작했습니다.확실하지 않음

  • 2010년대

    Kafka 같은 로그 기반 시스템이 퍼지면서 '로그가 곧 진실'이라는 발상이 널리 받아들여졌습니다.

이벤트 소싱은 누가 발명했다기보다 여러 갈래가 만난 지점에 가깝습니다. 회계의 장부, 데이터베이스의 트랜잭션 로그, 버전 관리 시스템의 커밋 — 전부 같은 아이디어입니다. 변화를 지우지 말고 쌓아라.

확실하지 않은 부분

'2005년경 Greg Young'은 커뮤니티에서 널리 통용되는 서술이지만 특정 날짜에 발표된 단일 논문이 있는 것은 아닙니다. 개념이 서서히 형성된 쪽에 가깝습니다.

05상황극 & 예시

은행 고객센터. 손님이 잔액이 이상하다며 찾아왔고, 개발자 민아가 불려 나왔다.

손님

분명히 50만원이 있었는데 지금 30만원이에요. 왜 이렇게 됐죠?

민아

(조회) 음... 잔액 칸에 300,000이라고만 적혀 있네요.

손님

그러니까 왜 그렇게 됐냐고요.

민아

...저희 시스템은 지금 얼마인지만 저장해서요. 어떻게 그렇게 됐는지는 기록이 없습니다.

손님

은행이요?

그래서 무슨 뜻이냐면

이벤트 소싱이었다면 민아의 화면에는 이렇게 떴을 겁니다. 입금 500,000 / 출금 150,000 / 출금 50,000. 잔액은 계산 결과일 뿐이고, 진실은 그 목록입니다. 답할 수 있는 시스템과 없는 시스템의 차이입니다.

실제 사건이 아니라 이해를 돕기 위해 만든 가상의 상황입니다. 다만 상태만 저장하는 시스템에서 이런 문의에 답하지 못하는 문제 자체는 실제로 흔합니다.

06본론

이벤트는 과거형으로 쓴다

이벤트는 이미 일어난 일입니다. 그래서 이름이 과거형이어야 합니다. WithdrawMoney는 명령이고, MoneyWithdrawn이 이벤트입니다. 명령은 거절될 수 있지만 이벤트는 거절할 수 없습니다. 이미 일어났으니까요.

같은 상황을 명령과 이벤트로 나눠 쓰면

// 명령 — 거절될 수 있다
{ type: 'WithdrawMoney', accountId: 'A1', amount: 50000 } // 이벤트 — 이미 일어난 일, 되돌릴 수 없다
{ type: 'MoneyWithdrawn', accountId: 'A1', amount: 50000, at: '2026-09-06T10:00:00Z' }

흔한 실수

이벤트 이름을 현재형으로 짓는 것. 그 순간부터 팀이 이벤트와 명령을 섞어 쓰게 되고, 이벤트 스토어에 '실패한 시도'가 섞여 들어갑니다.

상태는 저장하지 않고 계산한다

현재 잔액이 필요하면 그 계좌의 이벤트를 처음부터 접습니다. 이걸 리플레이(replay) 또는 폴드(fold)라고 부릅니다. 함수형 프로그래밍의 reduce 와 정확히 같은 연산입니다.

이벤트 목록을 접어 잔액을 만든다

const balance = events.reduce((acc, e) => e.type === 'MoneyDeposited' ? acc + e.amount : e.type === 'MoneyWithdrawn' ? acc - e.amount : acc
, 0)

흔한 실수

이벤트가 수만 개 쌓인 뒤에도 매번 처음부터 접는 것. 스냅샷(중간 결산)을 두고 그 뒤부터만 접어야 합니다.

이벤트 스토어는 append-only 다

이벤트는 수정도 삭제도 하지 않습니다. 잘못 저장했다면 정정 이벤트를 새로 추가합니다. 회계의 반대 분개와 같습니다. 이 규칙을 한 번이라도 깨면 '기록이 진실'이라는 전제가 무너지고, 이벤트 소싱의 장점이 전부 사라집니다.

흔한 실수

"이번만 DB에서 직접 고치자"는 유혹. 그 순간 리플레이 결과와 실제가 어긋나고, 원인을 찾는 데 며칠이 걸립니다.

그래서 언제 쓰면 안 되는가

이벤트 소싱은 공짜가 아닙니다. 조회가 복잡해지고, 이벤트 스키마를 바꾸기 어렵고, 팀 전체가 이 모델을 이해해야 합니다. '어떻게 이 상태가 되었는가'를 아무도 묻지 않는 도메인이라면 쓰지 마세요. 단순 CRUD 게시판에 이걸 얹는 것은 명백한 과설계입니다.

흔한 실수

멋져 보인다는 이유로 전체 시스템에 적용하는 것. 보통은 계좌·주문처럼 이력이 중요한 일부 영역에만 씁니다.

07꿀팁

이벤트 이름은 업무 담당자가 쓰는 말로

'주문완료됨'을 개발자가 'OrderStatusUpdated'로 바꾸는 순간 코드와 대화가 어긋납니다. 도메인 전문가가 알아듣는 이름이 좋은 이벤트 이름입니다.

이벤트에 계산된 값을 넣지 말 것

'출금 5만원'만 저장하고 '남은 잔액 30만원'은 넣지 마세요. 계산 규칙이 바뀌면 과거 이벤트가 전부 거짓말이 됩니다.

스냅샷은 성능 문제가 실제로 생긴 뒤에

처음부터 스냅샷을 넣으면 복잡도만 오릅니다. 이벤트 수천 개까지는 그냥 접어도 충분히 빠릅니다.

이벤트 버전을 처음부터 넣어두기

스키마는 반드시 바뀝니다. version 필드가 없으면 나중에 과거 이벤트를 어떻게 읽어야 할지 알 수 없습니다.

08질의 5개

  1. 이벤트 스토어에 저장되는 것은 '현재 상태'인가요, '일어난 변화'인가요?

    정답 보기

    정답 일어난 변화(이벤트)입니다. 현재 상태는 그 변화들을 처음부터 접어서 계산해냅니다.

    이벤트 소싱의 정의 그 자체입니다. 상태는 저장 대상이 아니라 계산 결과입니다.

  2. 다음 중 이벤트 이름으로 올바른 것은?

    • WithdrawMoney
    • MoneyWithdrawn
    • WithdrawingMoney
    • MoneyWithdrawRequest
    정답 보기

    정답 MoneyWithdrawn

    이벤트는 이미 일어난 일이므로 과거형입니다. WithdrawMoney 는 거절될 수 있는 명령이고, Request 는 아직 일어나지 않은 요청입니다.

  3. 잘못 저장된 이벤트를 발견했습니다. 어떻게 고쳐야 하나요?

    정답 보기

    정답 수정하지 않고 정정 이벤트를 새로 추가합니다.

    이벤트 스토어는 append-only 입니다. 회계에서 틀린 분개를 지우지 않고 반대 분개를 적는 것과 같습니다. 직접 수정하면 리플레이 결과와 실제가 영구히 어긋납니다.

  4. 이벤트에 '남은 잔액 30만원' 같은 계산된 값을 넣으면 왜 위험한가요?

    정답 보기

    정답 계산 규칙이 바뀌면 과거 이벤트에 박힌 값이 전부 틀린 기록이 되기 때문입니다.

    이벤트는 '일어난 사실'만 담아야 합니다. 파생된 값은 리플레이 시점에 계산합니다.

  5. 사내 공지사항 게시판을 이벤트 소싱으로 만들자는 제안이 나왔습니다. 반대한다면 어떤 근거를 대겠습니까?

    정답 보기

    정답 '어떻게 이 상태가 되었는가'를 아무도 묻지 않는 도메인이기 때문입니다.

    이벤트 소싱은 이력 추적과 감사가 가치를 만드는 곳에서 값을 합니다. 공지 게시판은 최신 내용만 중요하고, 조회 복잡도와 학습 비용만 늘어납니다. 명백한 과설계입니다.

09숙제 & 과제

내 통장을 이벤트로 다시 쓰기

최근 은행 거래 내역 10건을 { type, amount, at } 형태의 이벤트 배열로 종이에 옮겨 적으세요. 그다음 그 배열을 위에서부터 접어서 현재 잔액을 손으로 계산하고, 실제 잔액과 맞는지 확인하세요.

예상 20분

정정 이벤트 설계해보기

위 이벤트 중 하나가 금액을 잘못 적었다고 가정하고, 그 이벤트를 지우지 않은 채 바로잡는 정정 이벤트를 설계해 적으세요. 이름은 반드시 과거형으로.

예상 15분

정답은 없습니다. 다만 '기존 이벤트를 고치지 않았는가'와 '이벤트 이름이 과거형인가' 두 가지만 스스로 확인하세요.

10마무리 팁

이렇게 씁니다

  • 주문 상태가 왜 '취소됨'이 되었는지 고객센터가 직접 확인할 수 있게 만들 때
  • 금융·의료처럼 감사 로그가 법적으로 요구되는 시스템
  • 협업 문서 편집기에서 되돌리기와 변경 이력을 구현할 때

일상에 붙이기

코드 밖에서도 써먹을 수 있습니다. 가계부를 '남은 돈'이 아니라 '쓴 내역'으로 적는 것, 일기를 '나는 요즘 우울하다'가 아니라 '오늘 무슨 일이 있었다'로 적는 것. 결론이 아니라 사건을 남기면 나중에 다른 결론도 뽑아낼 수 있습니다.

스스로 점검

  • 명령과 이벤트의 차이를 예로 설명할 수 있다
  • append-only 를 어겼을 때 무슨 일이 생기는지 말할 수 있다
  • 이벤트 소싱을 쓰지 말아야 할 상황을 하나 이상 댈 수 있다

11다음 단계 제안

CQRS

이벤트 소싱을 쓰면 조회가 불편해지는데, 그 문제를 정면으로 다루는 패턴입니다. 거의 항상 함께 등장합니다.

한 단계 더 깊게

스냅샷과 프로젝션

이벤트가 쌓였을 때의 성능 문제와, 조회용 읽기 모델을 만드는 방법을 다룹니다.

한 단계 더 깊게

도메인 주도 설계(DDD)의 애그리거트

이벤트를 '어느 단위로' 묶을지를 결정하는 개념입니다. 이걸 알면 이벤트 설계가 훨씬 쉬워집니다.
